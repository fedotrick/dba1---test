  ТЕМА 1: Введение. Архитектура PostgreSQL

  Теория простым языком

  Что такое PostgreSQL?

  PostgreSQL — это объектно-реляционная СУБД (ORDBMS). Простыми словами: база данных, которая хранит данные в таблицах,
  но при этом поддерживает объекты (наследование, типы данных, функции) как в объектно-ориентированных языках.

  Клиент-серверная архитектура

  PostgreSQL работает по схеме клиент-сервер:

  Клиент (psql, приложение)
      → Подключение + Аутентификация
      → Сервер (PostgreSQL)
      → Транзакция (BEGIN...COMMIT)
      → Результат обратно клиенту

  - Клиент — любая программа, которая умеет говорить по протоколу PostgreSQL (psql, JDBC, Python-клиент и т.д.)
  - Сервер — процесс postgres, который управляет БД, обрабатывает запросы, записывает данные

  Три важных факта о PostgreSQL:

  1. ACID — транзакции гарантируют атомарность, согласованность, изоляцию и долговечность
  2. MVCC — мультиверсионность: несколько версий одной строки существуют одновременно, что позволяет читающим
  транзакциям не блокировать пишущие
  3. WAL — журнал предзаписи: прежде чем записать данные на диск, сервер записывает их в журнал (это обеспечивает
  восстановление после сбоя)

  Структура экземпляра PostgreSQL:

  Экземпляр = набор процессов + общая память + кластер БД
      │
      ├── Кластер БД (data directory)
      │     ├── base/        — данные таблиц
      │     ├── global/      — системные данные
      │     ├── pg_wal/      — журнал
      │     └── pg_tblspc/   — tablespaces
      │
      └── Несколько баз данных внутри кластера

  Важно: Кластер — это не кластер репликации. Это термин PostgreSQL для обозначения одной инсталляции: коллекции баз
  данных под одним сервером.

  ТЕМА 2: Установка и настройка PostgreSQL

  Теория простым языком

  Как установить PostgreSQL

  Есть несколько способов:

  ┌──────────────────────────────┬───────────────────────────────────────┐
  │            Способ            │          Когда используется           │
  ├──────────────────────────────┼───────────────────────────────────────┤
  │ Пакетный менеджер (apt, yum) │ Быстрая установка на Linux            │
  ├──────────────────────────────┼───────────────────────────────────────┤
  │ Инсталлятор (PostgreSQL.com) │ Windows, macOS                        │
  ├──────────────────────────────┼───────────────────────────────────────┤
  │ Исходный код                 │ Кастомные сборки, изучение исходников │
  ├──────────────────────────────┼───────────────────────────────────────┤
  │ Докер                        │ Тестирование, разработка              │
  └──────────────────────────────┴───────────────────────────────────────┘

  На Linux (RHEL/CentOS):
  sudo yum install -y postgresql-server postgresql-contrib
  sudo postgresql-setup --initdb
  sudo systemctl enable postgresql
  sudo systemctl start postgresql

  Каталог данных (PGDATA)

  Это корневая папка, где PostgreSQL хранит всё:
  PGDATA/
  ├── base/          — таблицы и индексы
  ├── global/        — системные таблицы (pg_roles, pg_database)
  ├── pg_wal/        — журнал транзакций
  ├── pg_xact/       — статус транзакций
  ├── pg_tblspc/     — симлинки на tablespaces
  └── postgresql.conf — ГЛАВНЫЙ КОНФИГ

  Переменная PGDATA — это путь к каталогу данных. Сервер читает её при старте.

  Пользователь postgres

  После установки создаётся системный пользователь postgres. Это суперпользователь ОС, от имени которого работает СУБД.
  Логиниться под ним напрямую — плохая практика в продакшене.

  Основные конфигурационные файлы:

  ┌─────────────────┬──────────────────────────────────────────────────────────┐
  │      Файл       │                        Назначение                        │
  ├─────────────────┼──────────────────────────────────────────────────────────┤
  │ postgresql.conf │ Параметры сервера (память, количество соединений и т.д.) │
  ├─────────────────┼──────────────────────────────────────────────────────────┤
  │ pg_hba.conf     │ Настройка аутентификации (кто может подключаться и как)  │
  ├─────────────────┼──────────────────────────────────────────────────────────┤
  │ pg_ident.conf   │ Маппинг ОС-пользователей на роли PostgreSQL              │
  └─────────────────┴──────────────────────────────────────────────────────────┘

  postgresql.conf — ключевые параметры:

  max_connections = 100          # Макс. число одновременных подключений
  shared_buffers = 128MB          # Память для буферного кеша
  effective_cache_size = 4GB      # Оценка доступной памяти для кеша ОС
  work_mem = 4MB                  # Память для сортировок/хешей на запрос
  maintenance_work_mem = 64MB    # Память для VACUUM, CREATE INDEX
  wal_level = replica            # minimal, replica, logical
  max_wal_senders = 10           # Число слейвов для репликации

  Команды управления сервером:

  pg_ctl start|stop|restart|status  # Управление сервером
  pg_isready                         # Проверка готовности
  pg_config --version                # Версия PostgreSQL

  Контрольные суммы (pg_checksums):
  
  # Проверить контрольные суммы
  pg_checksums --check -D $PGDATA
  
  # Включить контрольные суммы (требует остановки)
  pg_checksums --enable -D $PGDATA

  Ubuntu/Debian специфика:
  
  pg_createcluster 16 main --create   # Создать кластер
  pg_dropcluster 16 main --drop      # Удалить кластер
  pg_lsclusters                        # Список кластеров

  initdb опции:
  initdb -k --data-checksums          # Включить контрольные суммы при создании

  ТЕМА 3: Инструменты psql

  Теория простым языком

  Что такое psql?

  psql — это CLI-клиент PostgreSQL. Терминальная программа для подключения к серверу и выполнения SQL-команд. Работает
  как интерактивная оболочка.

  Подключение:
  psql -h localhost -p 5432 -U postgres -d mydb
  # -h хост, -p порт, -U пользователь, -d база

  # Или через переменные окружения:
  export PGHOST=localhost
  export PGPORT=5432
  export PGUSER=postgres
  export PGDATABASE=mydb
  psql

  Метакоманды psql (начинаются с )

  ┌─────────────────┬──────────────────────────────────────────────────────┐
  │     Команда     │                      Что делает                      │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \l или \list    │ Список всех баз данных                               │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \c mydb         │ Подключиться к базе mydb                             │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \dt             │ Список таблиц в текущей схеме                        │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \di             │ Список индексов                                      │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \dv             │ Список представлений (views)                         │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \d table_name   │ Описание таблицы (структура)                         │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \d+ table_name  │ Подробное описание таблицы                           │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \df             │ Список функций                                       │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \dn             │ Список схем                                          │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \du             │ Список ролей/пользователей                           │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \dp             │ Список привилегий                                    │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \x              │ Переключить вывод в "расширенный" режим (по строкам) │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \h CREATE TABLE │ Справка по SQL-команде                               │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \?              │ Список всех метакоманд                               │
  ├─────────────────┼──────────────────────────────────────────────────────┤
  │ \timing         │ Включить/выключить показ времени выполнения          │

  │ \echo :VARIABLE │ Показать значение переменной                         │
  └─────────────────┴──────────────────────────────────────────────────────┘

  Полезные переменные psql:

  -- Посмотреть текущие настройки
  SHOW ALL;

  -- Показать текущую базу данных
  SELECT current_database();

  -- Текущего пользователя
  SELECT current_user;

  -- Версию PostgreSQL
  SELECT version();

  Настройка приглашения (prompt)

  Можно настроить вид приглашения psql через переменную PROMPT:

  \set PROMPT1 '%[%033[1;31m%]%M %/%R%#%[%033[0m%] '
  -- Покажет: хост/база/# для суперпользователя

  Работа с файлами:

  -- Выполнить команды из файла

  -- Скопировать данные в CSV

  -- Вывести результат в файл
  \o /tmp/output.txt

  -- Задать переменную
  \set name 'value'

  -- Использовать в запросе
  SELECT :name;  -- подставит 'value'

  -- Обнулить
  \unset name

  ТЕМА 4: Конфигурация сервера

  Теория простым языком

  Три главных файла конфигурации

  postgresql.conf    — параметры работы сервера
  pg_hba.conf       — правила аутентификации
  pg_ident.conf     — маппинг ОС-пользователей на роли PostgreSQL

  Все файлы редактируются текстовым редактором. После изменения — перезагрузка или перезапуск сервера.

  Методы изменения параметров:

  1. Через postgresql.conf (или через ALTER SYSTEM)
  # Редактируем postgresql.conf
  max_connections = 200

  # Перезагружаем (не перезапускаем)
  pg_ctl reload
  # или: SELECT pg_reload_conf();

  2. Через SQL (ALTER SYSTEM) — современный способ:
  ALTER SYSTEM SET shared_buffers = '256MB';
  -- Записывает в postgresql.auto.conf (приоритетнее postgresql.conf)
  SELECT pg_reload_conf();

  3. Через SET (временное, для текущей сессии):
  SET work_mem = '16MB';
  SHOW work_mem;  -- покажет текущее значение
  RESET work_mem; -- вернуть к default

  4. Просмотр параметров:
  SHOW all;                          -- все параметры
  SHOW max_connections;              -- конкретный
  SELECT * FROM pg_settings WHERE name LIKE 'shared_buffers%';

  Важнейшие параметры для настройки:

  1. Параметры памяти:
  shared_buffers = 256MB      # 25% от RAM, но не больше 8GB на 64-bit
  effective_cache_size = 4GB  # Оценка памяти ОС для кеша (75% RAM)
  work_mem = 4MB              # На каждую операцию сортировки/хеша
  maintenance_work_mem = 64MB # Для VACUUM, CREATE INDEX (лучше больше)

  2. Параметры WAL:
  wal_level = replica          # minimal | replica | logical
  max_wal_senders = 10        # Сколько реплик может быть
  wal_buffers = 16MB           # Буфер для WAL (обычно 1/32 от shared_buffers)

  3. Параметры запросов:
  shared_preload_libraries = 'pg_stat_statements'  # Расширение статистики
  max_connections = 100       # Макс. одновременных подключений

  pg_hba.conf — формат записей:

  # Тип подключения | База данных | Пользователь | Адрес | Метод аутентификации
  # -------------------------------------------------------
  local     all     postgres          peer
  local     all     all               scram-sha-256
  host      all     all       127.0.0.1/32    scram-sha-256
  host      all     all       0.0.0.0/0       md5
  host      replication     replicator  0.0.0.0/0     scram-sha-256

  Типы подключения:
  - local — через Unix-сокет (с сервера)
  - host — через TCP/IP (может быть SSL)
  - hostssl — только SSL-соединения

  Методы аутентификации:

  ┌─────────────────────┬──────────────────────────────────────────────────────────────────────┐
  │        Метод        │                          Когда использовать                          │
  ├─────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ trust               │ Локальное подключение, доверенные пользователи (НЕ для продакшена!)  │
  ├─────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ peer                │ Локальное, проверка что ОС-пользователь совпадает с ролью PostgreSQL │

  ТЕМА 5: Архитектура. Общее устройство

  Теория простым языком

  Как устроен PostgreSQL изнутри

  PostgreSQL — это мультипроцессная система. Главный процесс — postmaster — порождает дочерние процессы для обработки
  каждого подключения.

  Структура процессов:

  postmaster (главный процесс)
      ├── writer (запись грязных буферов на диск)
      ├── wal writer (запись WAL на диск)
      ├── autovacuum launcher (запуск автоочистки)
      ├── bgwriter (фоновая запись)
      ├── stats collector (сбор статистики)
      └── postgres (обслуживание клиента) × N

  Общая память (shared memory):

  shared_buffers ─────→ Буферный кеш страниц данных (8KB каждая)
  wal_buffers    ─────→ Буфер журнала WAL (перед записью на диск)

  Как обрабатывается запрос:

  Клиент
     ↓
  1. Установление соединения (postmaster → форк postgres)
     ↓
  2. Разбор запроса (parsing) — синтаксис, таблицы, столбцы
     ↓
  3. Планиение (planning) — выбор оптимального пути выполнения
     ↓
  4. Выполнение (execution) — чтение данных, применение изменений
     ↓
  5. Возврат результата клиенту

  Транзакции — основы

  BEGIN;                        -- или START TRANSACTION
    INSERT INTO users VALUES (1, 'Alice');
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  COMMIT;                       -- или ROLLBACK для отката

  ACID на примере:

  - Atomicity (Атомарность): Если в транзакции 3 операции — либо все применятся, либо ни одна. Даже при сбое.
  - Consistency (Согласованность): Транзакция переводит БД из одного согласованного состояния в другое. Если есть
  ограничения (CHECK, FK, UNIQUE) — нарушение откатит транзакцию.
  - Isolation (Изоляция): Параллельные транзакции не мешают друг другу. Подробнее — уровни изоляции.
  - Durability (Долговечность): Зафиксированные данные не пропадут — они либо в журнале, либо на диске.

  Уровни изоляции (от слабого к сильному):

  ┌──────────────────┬────────────────────────────────────────────────────────────────────┐
  │     Уровень      │                          Что гарантирует                           │
  ├──────────────────┼────────────────────────────────────────────────────────────────────┤
  │ READ UNCOMMITTED │ Видит незафиксированные данные (почти не используется в PG)        │
  ├──────────────────┼────────────────────────────────────────────────────────────────────┤
  │ READ COMMITTED   │ Видит только зафиксированные данные (ПО УМОЛЧАНИЮ)                 │
  ├──────────────────┼────────────────────────────────────────────────────────────────────┤
  │ REPEATABLE READ  │ Снимок с начала транзакции, повторные чтения дают тот же результат │
  ├──────────────────┼────────────────────────────────────────────────────────────────────┤
  │ SERIALIZABLE     │ Полная изоляция, транзакции выполняются как будто последовательно  │
  └──────────────────┴────────────────────────────────────────────────────────────────────┘

  Блокировки

  Блокировки нужны чтобы транзакции не мешали друг другу:

  SELECT ... FOR UPDATE;  -- Блокировка строки для изменения
  LOCK TABLE orders;      -- Блокировка таблицы

  Типы блокировок:
  - Взаимные (row-level): Две транзакции борются за одну строку
  - Табличные: Блокировка всей таблицы
  - Бесконфликтные: Разные типы блокировок могут coexist

  SAVEPOINT — точки сохранения в транзакции:

  BEGIN;
    INSERT INTO t VALUES (1);
    SAVEPOINT sp1;
    INSERT INTO t VALUES (2);
    ROLLBACK TO sp1;  -- откатываем до точки
    INSERT INTO t VALUES (3);
  COMMIT;  -- в итоге: 1 и 3

  PREPARE/EXECUTE — подготовленные запросы:

  PREPARE q(id int) AS SELECT * FROM t WHERE id = $1;
  EXECUTE q(1);
  EXECUTE q(2);

  Курсоры в транзакциях:

  DECLARE c CURSOR FOR SELECT * FROM t;
  FETCH 10 FROM c;
  CLOSE c;

  psql настройки (важное для практики):

  \set ON_ERROR_ROLLBACK on  -- авто-savepoint при ошибке (интерактивно)
  \set ON_ERROR_STOP on      -- остановить при первой ошибке

  ~/.psqlrc — автоматическая настройка при запуске:
  \setenv PSQL_PAGER 'less -XS'
  \timing on
  PROMPT1 '%n@%/%R%x%# '

  ТЕМА 6: MVCC — многоверсионность

  Теория простым языком

  Что такое MVCC и зачем он нужен

  MVCC расшифровывается как Multi-Version Concurrency Control — многоверсионное управление параллелизмом.

  Проблема без MVCC:
  - Транзакция A читает строку X
  - Транзакция B одновременно пытается изменить строку X
  - Какой результат видит A? Что происходит с B?

  Решение MVCC: Каждая транзакция видит снимок данных (snapshot) — свою версию базы на определённый момент времени.
  Пишущие не блокируют читающих.

  Как это работает в PostgreSQL:

  У каждой строки есть два скрытых поля:
  - xmin — кто создал эту версию (ID транзакции)
  - xmax — кто последний её изменил (или удалил)

  Версия строки: [данные] xmin=100 xmax=101

  Жизненный цикл строки:

  INSERT:          Новая строка с xmin=текущая_транзакция, xmax=NULL
                  ↓
  UPDATE:          Старая версия получает xmax=текущая_транзакция
                  Создаётся НОВАЯ версия с xmin=текущая_транзакция, xmax=NULL
                  ↓
  DELETE:          Строка получает xmax=текущая_транзакция (логическое удаление)

  Снимок (snapshot) — это информация:
  - Какой номер транзакции сейчас
  - Список активных (ещё не зафиксированных) транзакций

  Снимок: { "текущий xid": 150, "активные": [145, 147, 148] }

  Транзакция с xid=152 при старте видит:
  - Все изменения от транзакций с xid < 152, КРОМЕ тех, что в активном списке

  Видимость строки — правила:

  Строка видна транзакции T если:
  1. xmin зафиксирован И не в активном списке
  2. xmin = T (своя транзакция создала)
  3. xmin <SnapshotStart, но транзакция зафиксирована

  Строка НЕ видна если:
  - xmax в активном списке (удалена正在ной транзакцией)
  - xmax = T (моя транзакция удалила)

  Статус транзакций:

  ┌─────────────┬────────────────────────────┐
  │   Статус    │         Что значит         │
  ├─────────────┼────────────────────────────┤
  │ IN PROGRESS │ Транзакция выполняется     │
  ├─────────────┼────────────────────────────┤
  │ COMMITTED   │ Зафиксирована (видна всем) │
  ├─────────────┼────────────────────────────┤
  │ ABORTED     │ Отменена (игнорируется)    │
  └─────────────┴────────────────────────────┘

  Проблемы MVCC:

  1. Версии накапливаются — старые версии занимают место → нужен VACUUM
  2. Версия видна всем, пока не зафиксируется — нет изоляции на READ UNCOMMITTED
  3. Снимок «живёт» долго — если транзакция открыта 2 часа, все старые версии должны храниться

  Hot Update уязвимость:

  Если транзакция A обновляет строку, а транзакция B хочет тоже её обновить:
  - B видит что строка заблокирована A
  - B ждёт

  Но есть проблема: index bloat — индексы тоже содержат ссылки на старые версии строк.

  ТЕМА 7: VACUUM — очистка

  Теория простым языком

  Зачем нужен VACUUM

  В MVCC при UPDATE/DELETE старые версии строк остаются в данных. Они помечаются как "мёртвые" (xmax указывает на活跃ную
   транзакцию, которая уже завершилась). Если их не удалять:

  - Таблица разрастается бесконечно
  - Индексы содержат ссылки на мёртвые строки
  - Запросы замедляются

  VACUUM — процесс очистки этих мёртвых версий.

  Что делает VACUUM:

  1. Удаляет мёртвые версии строк из табличных страниц
  2. Очищает индексы от ссылок на мёртвые строки
  3. Обновляет карту видимости (Visibility Map) — какие страницы содержат только актуальные данные
  4. Помечает освобождённое пространство как доступное для новых данных

  Автоочистка (autovacuum)

  PostgreSQL запускает VACUUM автоматически. Параметры:

  autovacuum = on                    # Включен по умолчанию
  autovacuum_max_workers = 3         # Макс. процессов очистки одновременно
  autovacuum_naptime = 1min         # Пауза между циклами
  autovacuum_vacuum_threshold = 50  # Порог: сколько мёртвых строк запускает очистку
  autovacuum_analyze_threshold = 50  # Порог для ANALYZE

  Формула запуска:
  Если (мёртвых строк > autovacuum_vacuum_threshold + ( таблица × autovacuum_vacuum_scale_factor ))

  По умолчанию autovacuum_vacuum_scale_factor = 0.2 (20% от таблицы).

  ANALYZE vs VACUUM

  ┌────────────────┬───────────────────────────────────────────┐
  │    Команда     │                Что делает                 │
  ├────────────────┼───────────────────────────────────────────┤
  │ VACUUM         │ Удаляет мёртвые версии, освобождает место │
  ├────────────────┼───────────────────────────────────────────┤
  │ ANALYZE        │ Обновляет статистику для планировщика     │
  ├────────────────┼───────────────────────────────────────────┤
  │ VACUUM ANALYZE │ И то, и другое                            │
  └────────────────┴───────────────────────────────────────────┘

  Статистика нужна планировщику чтобы выбирать правильные индексы и методы join.

  Freeze

  Когда версия строки становится очень старой, её xmin может «пересечься» с счётчиком транзакций. Чтобы избежать
  проблемы «xid wraparound» (когда счётчик переполняется), VACUUM замораживает старые строки — вместо xmin ставится
  специальную метку.

  -- Проверить статус заморозки
  SELECT relname, n_live_tup, n_dead_tup, last_vacuum, freeze_age
  FROM pg_stat_user_tables;

  Ручной запуск:

  VACUUM table_name;           -- Очистить конкретную таблицу
  VACUUM ANALYZE table_name;    -- Очистка + анализ
  VACUUM FULL table_name;      -- Полная перестроение (блокирует таблицу!)

  VACUUM FULL — перестраивает таблицу полностью. Работает долго, блокирует таблицу. Используй только в крайнем случае.
  Для больших таблиц — CLUSTER или pg_repack.

  Что влияет на эффективность VACUUM:

  maintenance_work_mem = 64MB    # Больше памяти = быстрее очистка
  vacuum_cost_delay = 0          # Задержка (0 = отключена, быстрее)
  vacuum_cost_limit = 1000       # Лимит "стоимости" очистки

  ТЕМА 8: WAL — журнал предзаписи

  Теория простым языком

  Что такое WAL

  WAL = Write-Ahead Log (журнал предзаписи). Это ключевой механизм для durability (долговечности данных).

  Идея простая: Прежде чем записать данные на диск, PostgreSQL записывает изменения в журнал. Даже если система упадёт —
   журнал есть, значит данные можно восстановить.

  Почему это важно:

  Без WAL: Записали данные → сбой → данные потеряны
  С WAL:    Записали в журнал → записали данные → сбой → восстановили из журнала

  Как работает WAL:

  Клиент: UPDATE users SET name='Bob' WHERE id=1;
      ↓
  1. Изменение записывается в буфер WAL (в оперативной памяти)
      ↓
  2. Буфер сбрасывается на диск (каждые wal_buffers или при commit)
      ↓
  3. Данные изменяются в буферном кеше (shared_buffers), НО на диск пока НЕ записаны
      ↓
  4. При commit — данные гарантированно в журнале (можно восстановить)
      ↓
  5. bgwriter периодически сбрасывает грязные буферы на диск

  Контрольная точка (checkpoint)

  Это момент, когда PostgreSQL гарантирует что все данные из буферного кеша записаны на диск. Журнал говорит: "до этой
  точки всё уже на диске".

  checkpoint_timeout = 5min      # Как часто делать контрольную точку
  max_wal_size = 1GB            # Макс. размер WAL до следующей контрольной точки
  min_wal_size = 80MB           # Минимум WAL для переиспользования

  Восстановление после сбоя:

  При старте PostgreSQL проверяет:
  6. Последняя контрольная точка
  7. Все записи журнала после неё — применить к данным

  Это как "перемотка вперёд" — журнал уже записан, значит данные консистентны.

  WAL и репликация:

  Физическая репликация использует WAL как источник данных:
  - Мастер записывает WAL
  - Реплика читает WAL и применяет те же изменения

  Без WAL репликация невозможна.

  Типы WAL:

  wal_level = minimal          # Только для crash recovery
  wal_level = replica           # + репликация (то что нужно для продакшена)
  wal_level = logical           # + логическая репликация

  Структура WAL:

  pg_wal/
  ├── 000000010000000000000001   # Первый WAL-сегмент (16 MB)
  ├── 000000010000000000000002   # Второй сегмент
  └── ...

  Каждый сегмент = 16 MB. Когда заполняется — переключается на новый.

  Архивирование WAL:

  archive_mode = on
  archive_command = 'cp %p /backup/wal/%f'
  # %p = путь к файлу, %f = имя файла

  Позволяет восстановить базу на любой момент времени (PITR — Point-In-Time Recovery).

  Команды для работы с WAL:

  -- Показать текущий WAL
  SELECT pg_current_wal_lsn();

  -- Показать место в WAL
  SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0');

  -- Принудительный checkpoint
  CHECKPOINT;

  -- Посмотреть статус архивирования
  SELECT * FROM pg_stat_archiver;

  ТЕМА 9: Буферный кеш

  Теория простым языком

  Зачем нужен буферный кеш

  Диски медленные. RAM быстрая. PostgreSQL не может держать все данные в памяти (база может быть терабайты). Буферный
  кеш — это прослойка между быстрой памятью и медленным диском.

  Запрос: "Дай строку с id=5"
      ↓
  Ищем в буферном кеше (shared_buffers)
      ↓
  Есть? → Вернуть сразу (БЫСТРО)
  Нет?  → Прочитать с диска → Положить в кеш → Вернуть

  Размер страницы — 8 KB (фиксированный, не меняется при обычной установке).

  Как работает буферный кеш:

  shared_buffers (например, 128 MB)
  ├── буфер 0: страница таблицы users (8 KB) + метаданные
  ├── буфер 1: страница индекс 1 (8 KB)
  ├── буфер 2: страница данных (8 KB)
  ...
  └── 128 MB / 8 KB = 16384 буферов

  Вытеснение (eviction): Когда нужно загрузить новую страницу, а свободных буферов нет — вытесняется наименее
  используемая (LRU — Least Recently Used).

  Грязные буферы: Страница, которую изменили, но ещё не записали на диск. bgwriter и writer асинхронно сбрасывают их на
  диск.

  Взаимодействие с ОС:

  PostgreSQL shared_buffers        ОС page cache (fs cache)
      │                              │
      │  данные читаются/пишутся      │
      │◄────────────────────────────►│
      │                              │
      └──────────────────────────────┘
                диск

  PostgreSQL использует page cache ОС через fsync. Это важно: данные могут быть в кеше ОС, но ещё не на диске физически.

  Параметры буферного кеша:

  shared_buffers = 128MB    # 25% от RAM (max 8GB на 64-bit)
  effective_cache_size = 4GB  # Оценка: сколько ОС может отдать под page cache

  effective_cache_size — это подсказка для планировщика, не реальное выделение. Если сумма shared_buffers +
  effective_cache_size покрывает всю базу — запросы будут использовать индексы.

  Холодный vs горячий кеш:

  - Холодный старт — данных нет в кеше, всё с диска, медленно
  - Горячий — популярные данные уже в памяти, быстро

  Это одна из причин, почему важно правильно настроить shared_buffers и иметь достаточно RAM.

  Посмотреть статистику кеша:

  -- Попадания/промахи буферного кеша
  SELECT
      sum(heap_blks_read) as reads,
      sum(heap_blks_hit) as hits,
      round(100.0 * sum(heap_blks_hit) / nullif(sum(heap_blks_hit + heap_blks_read), 0), 2) as cache_hit_ratio
  FROM pg_statio_user_tables;

  -- Подробнее по таблицам
  SELECT relname, heap_blks_read, heap_blks_hit,
      round(100.0 * heap_blks_hit / nullif(heap_blks_hit + heap_blks_read, 0), 2) as ratio
  FROM pg_statio_user_tables ORDER BY ratio;

  Идеальный показатель — выше 95-99%. Ниже 90% — проблема.

  Буфер для WAL:

  wal_buffers = 16MB   # 1/32 от shared_buffers (авто)

  WAL буфер — это область памяти для ещё не записанных на диск записей журнала.

  ТЕМА 10: Базы данных и схемы

  Теория простым языком

  Кластер = экземпляр PostgreSQL

  Кластер — это коллекция баз данных под одним сервером. Термин "кластер" здесь не про репликацию!

  Экземпляр PostgreSQL (кластер)
  ├── База данных 1 (postgres)
  ├── База данных 2 (mydb)
  ├── База данных 3 (analytics)
  └── ... и т.д.

  Схема = пространство имён внутри базы

  Схема — это способ организовать объекты (таблицы, функции, индексы) внутри одной базы данных.

  База данных: mydb
  ├── Схема: public      (по умолчанию)
  ├── Схема: analytics
  ├── Схема: logging
  └── Схема: pg_catalog  (системная)

  Для чего нужны схемы:

  1. Логическая группировка — Tables в "sales", Functions в "utils"
  2. Разделение доступа — разные схемы для разных приложений
  3. Избежание конфликтов имён — две таблицы "users" в разных схемах

  Путь поиска (search_path)

  Когда вы пишете SELECT * FROM users, PostgreSQL ищет таблицу "users" в схемах по порядку:

  SHOW search_path;  -- по умолчанию: "$user", public

  -- Можно изменить:
  SET search_path TO analytics, public;

  -- Или на уровне базы:
  ALTER DATABASE mydb SET search_path TO analytics;

  Стандартные схемы:

  ┌────────────────────┬──────────────────────────────────────────────────┐
  │       Схема        │                    Назначение                    │
  ├────────────────────┼──────────────────────────────────────────────────┤
  │ pg_catalog         │ Системный каталог (таблицы, индексы, типы)       │
  ├────────────────────┼──────────────────────────────────────────────────┤
  │ information_schema │ Стандартный SQL интерфейс для метаданных         │
  ├────────────────────┼──────────────────────────────────────────────────┤
  │ public             │ Схема по умолчанию для пользовательских объектов │
  └────────────────────┴──────────────────────────────────────────────────┘

  Шаблоны (template0, template1)

  При создании новой базы данных — она клонируется из шаблона.

  - template1 — рабочий шаблон, можно добавлять объекты
  - template0 — чистый шаблон, не меняется

  -- Создать базу
  CREATE DATABASE mydb;

  -- Создать базу из другого шаблона
  CREATE DATABASE mydb2 TEMPLATE template0;

  -- Посмотреть базы
  \l

  Создание схемы:

  CREATE SCHEMA analytics;

  -- Создать объект в схеме:
  CREATE TABLE analytics.sales (...);

  -- Изменить search_path для текущей сессии:
  SET search_path TO analytics;

  Удаление схемы:

  DROP SCHEMA analytics;          -- только если схема пустая
  DROP SCHEMA analytics CASCADE;  -- удалить со всеми объектами

  Полезные представления:

  -- Список схем
  SELECT nspname FROM pg_namespace;

  -- Список таблиц в схеме
  SELECT table_schema, table_name FROM information_schema.tables
  WHERE table_schema NOT IN ('pg_catalog', 'information_schema');

  ТЕМА 11: Системный каталог

  Теория простым языком

  Что такое системный каталог

  Системный каталог — это набор таблиц и представлений, которые хранят метаинформацию о самой базе данных: таблицы,
  индексы, типы данных, функции, роли, права доступа.

  По сути это "база данных о базе данных".

  Два интерфейса к каталогу:

  ┌────────────────────┬─────────────────────────────────────────┐
  │     Интерфейс      │                Описание                 │
  ├────────────────────┼─────────────────────────────────────────┤
  │ pg_catalog         │ PostgreSQL-специфичный, содержит всё    │
  ├────────────────────┼─────────────────────────────────────────┤
  │ information_schema │ Стандартный SQL, переносимый между СУБД │
  └────────────────────┴─────────────────────────────────────────┘

  -- Пример: список таблиц
  SELECT * FROM information_schema.tables
  WHERE table_schema = 'public';

  -- То же через pg_catalog
  SELECT * FROM pg_catalog.pg_tables
  WHERE schemaname = 'public';

  pg_catalog — основные таблицы:

  ┌──────────────┬─────────────────────────────────────────────────────┐
  │   Таблица    │                     Что хранит                      │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_class     │ Таблицы, индексы, последовательности, представления │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_attribute │ Столбцы таблиц                                      │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_type      │ Типы данных                                         │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_proc      │ Функции и процедуры                                 │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_namespace │ Схемы                                               │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_database  │ Базы данных кластера                                │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_roles     │ Роли                                                │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_tables    │ Информация о таблицах                               │
  ├──────────────┼─────────────────────────────────────────────────────┤
  │ pg_indexes   │ Информация об индексах                              │
  └──────────────┴─────────────────────────────────────────────────────┘

  Как это выглядит на практике:

  -- Хотим узнать структуру таблицы users
  \d users
  -- Результат: имя, тип, nullable, default

  -- Что за кулисами — запрос к pg_attribute:
  SELECT attname, atttypid::regtype, attnotnull, attdefault
  FROM pg_attribute
  WHERE attrelid = 'users'::regclass AND attnum > 0;

  Специальные типы данных в каталоге:

  ┌──────────┬───────────────────────────────┐
  │   Тип    │         Что означает          │
  ├──────────┼───────────────────────────────┤
  │ regclass │ Ссылка на таблицу (OID + имя) │
  ├──────────┼───────────────────────────────┤
  │ regtype  │ Ссылка на тип данных          │
  ├──────────┼───────────────────────────────┤
  │ regproc  │ Ссылка на функцию             │
  ├──────────┼───────────────────────────────┤
  │ oidid    │ Идентификатор объекта         │
  └──────────┴───────────────────────────────┘

  -- regclass автоматически преобразует имя в OID и обратно
  SELECT 'users'::regclass;  -- вернёт users
  SELECT 'users'::regclass::oid;  -- вернёт 12345 (числовой OID)

  Изменение каталога:

  -- Создать таблицу = добавить строку в pg_class и pg_attribute
  CREATE TABLE t (id int);

  -- Удалить = убрать строки из каталога
  DROP TABLE t;

  -- Нельзя редактировать каталог напрямую (без очень веской причины!)

  Полезные запросы:

  -- Все таблицы с их размерами
  SELECT relname, pg_size_pretty(pg_total_relation_size(quote_ident(relname)::regclass))
  FROM pg_stat_user_tables ORDER BY pg_total_relation_size(quote_ident(relname)::regclass) DESC;

  -- Список индексов таблицы
  SELECT indexname, indexdef
  FROM pg_indexes
  WHERE tablename = 'users';

  -- Атрибуты таблицы
  SELECT attname, format_type(atttypid, atttypmod) as type
  FROM pg_attribute
  WHERE attrelid = 'users'::regclass AND attnum > 0;

  pg_stat_* vs pg_statio_*:

  ┌───────────────────────┬────────────────────────────────────────────────────┐
  │     Представление     │                   Что показывает                   │
  ├───────────────────────┼────────────────────────────────────────────────────┤
  │ pg_stat_user_tables   │ Статистика использования (чтение/запись)           │
  ├───────────────────────┼────────────────────────────────────────────────────┤
  │ pg_statio_user_tables │ Статистику I/O (попадания в буферы/чтение с диска) │
  └───────────────────────┴────────────────────────────────────────────────────┘

  ТЕМА 12: Tablespaces (табличные пространства)

  Теория простым языком

  Что такое tablespace

  Tablespace — это указание на каталог в файловой системе, где будут храниться данные. Позволяет:
  - Разместить данные на разных дисках
  - Управлять производительностью (быстрые SSD для горячих данных)
  - Расширить хранилище

  Стандартные tablespaces:

  ┌────────────┬──────────────────────────────────────┬────────────────┐
  │ Tablespace │              Что хранит              │      Путь      │
  ├────────────┼──────────────────────────────────────┼────────────────┤
  │ pg_default │ Пользовательские данные по умолчанию │ PGDATA/base/   │
  ├────────────┼──────────────────────────────────────┼────────────────┤
  │ pg_global  │ Системные данные (роли, базы)        │ PGDATA/global/ │
  └────────────┴──────────────────────────────────────┴────────────────┘

  Создание tablespace:

  -- Создать каталог на сервере
  mkdir -p /data/fastSSD tablespace

  -- Создать tablespace (выполняет суперпользователь)
  CREATE TABLESPACE fast_data LOCATION '/data/fastSSD';

  Использование tablespace:

  -- При создании таблицы
  CREATE TABLE hot_data (...) TABLESPACE fast_data;

  -- Переместить существующую
  ALTER TABLE old_data SET TABLESPACE fast_data;

  -- Переместить индекс
  ALTER INDEX big_index SET TABLESPACE fast_data;

  Просмотр tablespaces:

  -- Список tablespaces
  \db

  -- Подробная информация
  SELECT * FROM pg_tablespace;

  ТЕМА 13: Низкоуровневая организация данных

  Теория простым языком

  Файлы данных

  Каждый объект (таблица, индекс, последовательность) хранится в отдельных файлах внутри каталога базы данных.

  PGDATA/base/12345/
  ├── 12345     (основной слой — данные таблицы)
  ├── 12345.1   (сегмент 1, если файл > 1GB)
  ├── 12345.2   (сегмент 2)
  ├── 12345_fsm (Free Space Map — карта свободного места)
  ├── 12345_vm  (Visibility Map — карта видимости)
  └── 12345_init (для нежурналируемых таблиц)

  Размер сегмента: Когда файл данных превышает 1 GB, PostgreSQL создаёт новый файл-сегмент (.1, .2 и т.д.).

  Слои (forks) объекта:

  ┌──────┬───────────────────────────────────────────────────────────────────┐
  │ Слой │                            Назначение                             │
  ├──────┼───────────────────────────────────────────────────────────────────┤
  │ main │ Собственно данные (версии строк)                                  │
  ├──────┼───────────────────────────────────────────────────────────────────┤
  │ fsm  │ Карта свободного пространства — где есть место для новых строк    │
  ├──────┼───────────────────────────────────────────────────────────────────┤
  │ vm   │ Visibility Map — какие страницы содержат только актуальные версии │
  ├──────┼───────────────────────────────────────────────────────────────────┤
  │ init │ Пустышка для нежурналируемых таблиц (только для восстановления)   │
  └──────┴───────────────────────────────────────────────────────────────────┘

  Free Space Map (FSM)

  Таблица занимает целые страницы (8 KB). Не все страницы заполнены полностью. FSM показывает, где есть свободное место.

  -- Посмотреть свободное место
  SELECT pg_freespace('orders');

  -- Подробнее по страницам
  SELECT * FROM pg_freespace('orders') ORDER BY avail;

  FSM обновляется при VACUUM. Планировщик использует FSM чтобы понять, куда вставлять новые строки.

  Visibility Map (VM)

  Хранит информацию: какие страницы содержат только актуальные версии строк (видные всем транзакциям).

  Зачем нужно:
  - VACUUM пропускает страницы, помеченные в VM (быстрее очистка)
  - Индексы могут пропускать проверку xmin/xmax на таких страницах

  TOAST — хранение длинных данных

  TOAST = The Oversized Attribute Storage Technique. Механизм для хранения данных, которые не помещаются в строку.

  Если текст/массив > 2KB → сжимается или выносится в отдельную таблицу

  ---PG хранит большие значения отдельно, в main-таблице только ссылка
  CREATE TABLE articles (
      id serial,
      content text  -- если content > 2KB, пойдёт в TOAST
  );

  TOAST-таблица невидима, создаётся автоматически. Можно управлять:

  -- Метод хранения для столбца
  CREATE TABLE t (
      doc text STORAGE EXTENDED  -- или PLAIN, EXTERNAL, MAIN
  );

  Типы хранения TOAST:

  ┌──────────┬──────────────────────────────────────────────┐
  │   Тип    │                   Описание                   │
  ├──────────┼──────────────────────────────────────────────┤
  │ PLAIN    │ Не сжимать, не выносить в TOAST              │
  ├──────────┼──────────────────────────────────────────────┤
  │ EXTENDED │ Сжимать, затем выносить в TOAST              │
  ├──────────┼──────────────────────────────────────────────┤
  │ EXTERNAL │ Не сжимать, но выносить в TOAST (для текста) │
  ├──────────┼──────────────────────────────────────────────┤
  │ MAIN     │ Выносить в TOAST, но не сжимать              │
  └──────────┴──────────────────────────────────────────────┘

  Чтение данных — порядок действий:

  1. Ищем файл таблицы по OID
  2. Проверяем Visibility Map — видима ли страница
  3. Читаем страницу (с диска или из буферного кеша)
  4. Ищем нужную версию строки по xmin/xmax
  5. Возвращаем данные

  Физическое расположение объектов:

  -- OID таблицы
  SELECT relname, relfilenode FROM pg_class WHERE relname = 'orders';

  -- Путь к файлам
  SELECT pg_relation_filepath('orders');

  -- Размер в байтах
  SELECT pg_relation_size('orders');

  -- Полный размер (с индексами)
  SELECT pg_total_relation_size('orders');

  Роли в PostgreSQL

  PostgreSQL использует роли вместо традиционных пользователей и групп. Роль может:
  - Подключаться к БД (атрибут LOGIN)
  - Создавать базы данных (CREATEDB)
  - Создавать другие роли (CREATEROLE)
  - Быть суперпользователем (SUPERUSER)

  -- Создать роль пользователя
  CREATE ROLE alice LOGIN PASSWORD 'secret123';

  -- Создать сразу с правами
  CREATE ROLE admin LOGIN PASSWORD 'secret' SUPERUSER CREATEDB CREATEROLE;

  -- Роль-группа
  CREATE ROLE analytics_team NOLOGIN;

  -- Добавить пользователя в группу
  GRANT analytics_team TO alice;

  Атрибуты роли:

  ┌─────────────┬─────────────────────────────────────────┐
  │   Атрибут   │              Что позволяет              │
  ├─────────────┼─────────────────────────────────────────┤
  │ LOGIN       │ Подключаться к серверу                  │
  ├─────────────┼─────────────────────────────────────────┤
  │ SUPERUSER   │ Всё без ограничений                     │
  ├─────────────┼─────────────────────────────────────────┤
  │ CREATEDB    │ Создавать базы данных                   │
  ├─────────────┼─────────────────────────────────────────┤
  │ CREATEROLE  │ Создавать и изменять роли               │
  ├─────────────┼─────────────────────────────────────────┤
  │ REPLICATION │ Использовать для репликации             │
  ├─────────────┼─────────────────────────────────────────┤
  │ BYPASSRLS   │ Обходить Row-Level Security             │
  ├─────────────┼─────────────────────────────────────────┤

  └─────────────┴─────────────────────────────────────────┘

  ТЕМА 15: Мониторинг

  Теория простым языком

  Цель мониторинга

  Мониторинг позволяет:
  - Видеть текущее состояние системы
  - Замечать проблемы до того как они станут критическими
  - Планировать ёмкость (capacity planning)

  Источники информации:

  1. Средства ОС — ps, top, iostat, vmstat
  2. Статистика PostgreSQL — представления pg_stat_*
  3. Журнал сервера — postgresql.conf → log_directory
  4. Внешние системы — Prometheus, Grafana, Zabbix

  pg_stat_activity — текущие активности

  -- Что сейчас происходит
  SELECT pid, usename, state, query, query_start
  FROM pg_stat_activity
  WHERE state != 'idle'
  ORDER BY query_start;

  Состояния процесса:

  ┌───────────────────────────────┬───────────────────────────────┐
  │           Состояние           │           Значение            │
  ├───────────────────────────────┼───────────────────────────────┤
  │ active                        │ Выполняет запрос              │
  ├───────────────────────────────┼───────────────────────────────┤
  │ idle                          │ Ожидает команды               │
  ├───────────────────────────────┼───────────────────────────────┤
  │ idle in transaction           │ В транзакции, но не выполняет │
  ├───────────────────────────────┼───────────────────────────────┤
  │ idle in transaction (aborted) │ Транзакция отменена           │
  ├───────────────────────────────┼───────────────────────────────┤
  │ waiting                       │ Ожидает блокировки            │
  └───────────────────────────────┴───────────────────────────────┘

  pg_stat_ — накопительная статистика*

  -- Статистика по таблицам
  SELECT * FROM pg_stat_user_tables
  WHERE relname = 'orders';

  -- Tuples fetched, updated, deleted, inserted
  -- Sequential scans vs index scans
  -- Blocks read vs hit (cache efficiency)

  pg_statio_ — статистика I/O*

  -- Попадания в буфер vs чтение с диска
  SELECT relname,
      heap_blks_read,
      heap_blks_hit,
      round(100.0 * heap_blks_hit / nullif(heap_blks_hit + heap_blks_read, 0), 1) as hit_ratio
  FROM pg_statio_user_tables;

  Хороший показатель — выше 95-99%. Ниже 90% — проблема с памятью или запросами.

  pg_stat_bgwriter — статистика записи

  SELECT * FROM pg_stat_bgwriter;

  - checkpoints_req — контрольные точки по запросу (проблема!)
  - checkpoint_write_time — время записи
  - buffers_clean — страниц записано bgwriter
  - buffers_backend_fsync — сколько раз бэкенд ждал fsync

  Сессии и блокировки:

  -- Заблокированные запросы
  SELECT blocked_locks.pid AS blocked_pid,
         blocking_locks.pid AS blocking_pid,
         blocked_activity.query AS blocked_query,
         blocking_activity.query AS blocking_query
  FROM pg_catalog.pg_stat_activity AS blocked_activity
  JOIN pg_catalog.pg_locks AS blocked_locks ON blocked_activity.pid = blocked_locks.pid
  JOIN pg_catalog.pg_locks AS blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  WHERE NOT blocked_locks.granted;

  pg_stat_replication — статус репликации:

  SELECT client_addr, state, sent_lsn, write_lsn, replay_lsn
  FROM pg_stat_replication;

  ТЕМА 16: Резервное копирование

  Теория простым языком

  Два вида резервного копирования

  ┌────────────┬───────────────────────────┬───────────────────────────────┬─────────────────────────────┐
  │    Вид     │           Суть            │             Плюсы             │           Минусы            │
  ├────────────┼───────────────────────────┼───────────────────────────────┼─────────────────────────────┤
  │ Логическое │ SQL-дамп (pg_dump)        │ Переносимость, выбор объектов │ Медленное восстановление    │
  ├────────────┼───────────────────────────┼───────────────────────────────┼─────────────────────────────┤
  │ Физическое │ Копия файлов данных + WAL │ Быстрое восстановление        │ Непереносимо между версиями │
  └────────────┴───────────────────────────┴───────────────────────────────┴─────────────────────────────┘

  Логическое копирование — pg_dump

  # Копия одной базы данных
  pg_dump -U postgres -d mydb -f mydb_backup.sql

  # Копия всех баз данных (включая роли)
  pg_dumpall -U postgres -f full_backup.sql

  # Копия конкретной таблицы
  pg_dump -U postgres -d mydb -t orders > orders_backup.sql

  # Форматы
  pg_dump -Fc mydb > mydb.dump        # Сжатый, кастомный
  pg_dump -Fd mydb -f dump_dir/      # Directory format
  pg_dump -Ft mydb > mydb.tar        # TAR

  Восстановление из pg_dump:

  # Восстановить базу (должна существовать)
  psql -U postgres -d mydb -f mydb_backup.sql

  # Из сжатого формата
  pg_restore -U postgres -d mydb mydb.dump

  # Восстановить на другую базу
  pg_restore -U postgres -d newdb mydb.dump

  # Полный кластер
  psql -U postgres -f full_backup.sql

  COPY — копирование таблицы

  -- Экспорт таблицы
  COPY orders TO '/tmp/orders.csv' WITH (FORMAT csv, HEADER);

  -- Импорт
  COPY orders FROM '/tmp/orders.csv' WITH (FORMAT csv, HEADER);

  Физическое копирование — pg_basebackup

  # Полная копия кластера (включая WAL)
  pg_basebackup -U postgres -D /backup/base -Ft -z -P
  # -D каталог назначения
  # -Ft формат tar
  # -z сжатие gzip
  # -P показать прогресс

  WAL — журнал транзакций

  # Включить архивирование
  archive_mode = on
  archive_command = 'cp %p /backup/wal/%f'

  Point-in-Time Recovery (PITR)

  Идея: Берём базовую копию + применяем WAL до нужного момента времени.

  # 1. Создать базовую резервную копию
  pg_basebackup -U postgres -D /backup/base

  # 2. Настроить восстановление
  # в postgresql.conf или в recovery.conf:
  restore_command = 'cp /backup/wal/%f %p'

  # 3. Опционально: восстановить до определённого времени
  # recovery_target_time = '2024-11-25 14:30:00'

  # 4. Запустить PostgreSQL в режиме восстановления

  Файлы для PITR:

  /backup/base/          — базовая резервная копия
  /backup/wal/          — архивные WAL-файлы
  postgresql.conf       — параметры восстановления

  pg_dump vs pg_basebackup:

  pg_dump    → Логический дамп    → Медленно, маленький, переносимо
  pg_basebackup → Физическая копия → Быстро, большое, только та же версия

  Стратегия резервного копирования:

  # Ежедневно: pg_basebackup
  0 2 * * * pg_basebackup -U postgres -D /backup/daily -Ft -z -P

  # Каждые 15 минут: архивировать WAL
  archive_command = 'cp %p /backup/wal/%f'

  ТЕМА 17: Физическая репликация

  Теория простым языком

  Зачем нужна репликация

  - Отказоустойчивость — если primary упадёт, replica продолжит работать
  - Масштабирование чтения — запросы SELECT можно отправлять на реплики
  - Бэкап — replica может быть источником для бэкапа

  Как работает физическая репликация

  Primary (мастер)                    Replica (резервный)
       │                                     │
       │  1. Записывает изменения в WAL      │
       │────────────────────────────►        │
       │  (файлы или поток)                  │
       │                                     │
       │  2. Replica принимает WAL           │
       │     и применяет к своим данным      │
       │                                     ▼
       │                            Данные идентичные

  Требования:
  - Бинарная совместимость (одинаковая версия PostgreSQL, ОС, архитектура)
  - Репликация всего кластера (нельзя выбрать отдельные таблицы)

  Настройка физической репликации:

  1. На primary — настроить права:

  # postgresql.conf
  wal_level = replica
  max_wal_senders = 5
  wal_keep_size = 0  # или 1GB

  # pg_hba.conf — разрешить репликацию
  host  replication  all  0.0.0.0/0  scram-sha-256

  2. На primary — создать слот репликации (опционально):

  SELECT * FROM pg_create_physical_replication_slot('replica1');
  -- Гарантирует что WAL не удалятся пока реплика их не получила

  3. На replica — создать резервную копию primary:

  # Создать базовую резервную копию в режиме репликации
  pg_basebackup -U postgres -h primary_host -D /var/lib/postgresql/data -R -P
  # -R создаёт standby.signal
  # -P показать прогресс

  4. На replica — настроить:

  # postgresql.conf
  primary_conninfo = 'host=primary_host port=5432 user=postgres'

  # Восстановление (recovery.conf или в postgresql.conf):
  restore_command = 'cp /wal_archive/%f %p'

  Файлы для репликации:

  standby.signal          — флаг "это replica"
  primary_conninfo        — как подключиться к primary

  Потоковая репликация vs архивирование:

  ┌───────────┬────────────────────────────────────────────────────────┐
  │   Метод   │                      Как работает                      │
  ├───────────┼────────────────────────────────────────────────────────┤
  │ Потоковая │ Replica подключается к primary и получает WAL по сети  │
  ├───────────┼────────────────────────────────────────────────────────┤
  │ Архивная  │ Primary копирует WAL в архив, replica читает из архива │
  └───────────┴────────────────────────────────────────────────────────┘

  Потоковая быстрее, но требует постоянного соединения.

  Статус репликации:

  -- На primary
  SELECT * FROM pg_stat_replication;

  -- Имя, адрес, отставание (lag)
  -- state: streaming, catchup, startup

  Отставание (lag):

  SELECT client_addr,
      sent_lsn - write_lsn AS write_lag,
      write_lsn - flush_lsn AS flush_lag,
      flush_lsn - replay_lsn AS replay_lag
  FROM pg_stat_replication;

  Управление:

  -- На primary: увидеть кто подключён
  SELECT pid, usesysid, usename, application_name, state
  FROM pg_stat_replication;

  -- На replica: проверить режим
  SELECT pg_is_in_recovery();
  -- Вернёт t (true) если это replica

  Переключение (failover):

  # На replica: остановить восстановление и стать primary
  pg_ctl promote

  # Или командой:
  SELECT pg_promote();

  ТЕМА 18: Логическая репликация

  Теория простым языком

  Отличие от физической репликации

  ┌─────────────┬────────────────────────────────┬────────────────────────┐
  │             │           Физическая           │       Логическая       │
  ├─────────────┼────────────────────────────────┼────────────────────────┤
  │ Уровень     │ Страницы, WAL                  │ Строки таблиц          │
  ├─────────────┼────────────────────────────────┼────────────────────────┤
  │ Объекты     │ Весь кластер                   │ Выбранные таблицы      │
  ├─────────────┼────────────────────────────────┼────────────────────────┤
  │ Направление │ Одностороннее (master→replica) │ Двустороннее (pub↔sub) │
  ├─────────────┼────────────────────────────────┼────────────────────────┤
  │ Версия      │ Только одинаковая              │ Может быть разной      │
  └─────────────┴────────────────────────────────┴────────────────────────┘

  Принцип работы:

  Publisher (публикующий)            Subscriber (подписчик)
       │                                   ▲
       │  1. Читает WAL                    │
       │  2. Декодирует в изменения строк  │
       │──────────────────────────►        │
       │  3. Отправляет подписчику         │
       │                                   │
       │  4. Применяет изменения           │
       ▼                                   │
     Данные                              Данные

  Ключевые компоненты:

  Публикация (Publication) — на сторонеpublisher:
  -- Создать публикацию для таблицы
  CREATE PUBLICATION my_pub FOR TABLE users, orders;

  -- Публикация только INSERT, UPDATE, DELETE (не TRUNCATE)
  CREATE PUBLICATION my_pub FOR TABLE users
      WITH (publish = 'insert, update');

  -- Публикация всех таблиц
  CREATE PUBLICATION all_tables FOR ALL TABLES;

  Подписка (Subscription) — на стороне subscriber:
  -- Создать подписку
  CREATE SUBSCRIPTION my_sub
      CONNECTION 'host=primary port=5432 dbname=mydb user=postgres'
      PUBLICATION my_pub;

  -- Подписка сINITIAL DATA — синхронизация начальных данных
  -- (по умолчанию ВКЛ)

  Настройка wal_level:

  wal_level = logical   # Нужен именно logical (не replica!)

  Уровни журнала для репликации:

  wal_level = minimal    # Только crash recovery
  wal_level = replica    # Физическая репликация
  wal_level = logical     # + Логическая репликация

  Логическая репликация vs физическая:

  Физическая:
  Master → Replica (binary, entire cluster)

  Логическая:
  Master → Replica (row changes, SELECTED tables)
  Master ← Replica (можно публиковать обратно!)

  Конфликты

  Логическая репликация может конфликтовать:

  -- Subscriber пытается вставить строку,
  -- которая уже есть и нарушает PK/unique

  -- Решения:
  -- 1. Удалить конфликтующую строку на subscriber
  -- 2. Задать направление данных правильно
  -- 3. Использовать REPLICA IDENTITY

  REPLICA IDENTITY — что передаётся для UPDATE/DELETE:

  -- По умолчанию: первичный ключ
  ALTER TABLE t REPLICA IDENTITY USING INDEX my_index;

  -- Всё (полная строка для сравнения)
  ALTER TABLE t REPLICA IDENTITY FULL;

  -- Ничего (нельзя обновлять/удалять)
  ALTER TABLE t REPLICA IDENTITY NONE;

  Мониторинг:

  -- Статус подписки
  SELECT * FROM pg_stat_subscription;

  -- Ошибки
  SELECT * FROM pg_subscription_rel;

  -- Список публикаций
  SELECT * FROM pg_publication;

  -- Таблицы в публикации
  SELECT * FROM pg_publication_tables;

  Преобразования данных:

  Логическая репликация позволяет манипулировать данными перед применением на подписчике — через трансформации (сложная
  тема, но суть: не просто копия, а можно фильтровать колонки, строки, преобразовывать).
